# Solution Architecture — Warehouse Labor Planning Tool

Defines the technical shape of the system: how it runs on a laptop for demo/show-and-tell purposes, and how that maps to the [ERD reference](reference/labor-planning-erd-reference-v2.md), the [Release Plan](RELEASE_PLAN.md), and the engineering standards in [CLAUDE.md](../CLAUDE.md) Section 2. This is a planning document under the [Development Gate](../CLAUDE.md#7-development-gate--documentation-before-code) — no code is written from it until approved.

## 1. Goal of this architecture

A downstream WMS/WFM/rostering system is real, external infrastructure this tool can't assume access to. To keep the tool credible ("tooling realism" per CLAUDE.md §2) while still being trivially runnable by anyone who clones the repo, we **mimic the upstream data sources locally**: a single-file SQLite database, seeded by a checked-in SQL script, stands in for what would otherwise be live WMS/HCM/OMS feeds. Nothing needs to be installed beyond the app's own runtime — no external DB server, no cloud dependency.

## 2. High-level architecture

```
┌─────────────────────────┐
│   Frontend (React/Vite) │   UI only — no direct DB access
│   talks to API over     │
│   HTTP/JSON             │
└───────────┬──────────────┘
            │ REST (JSON)
┌───────────▼──────────────┐
│  Backend API (FastAPI)   │   Business logic: task engine, requirement
│  - Input layer services  │   calc, matching, governance, observability
│  - Task layer services   │
│  - Output layer services │
│  - Governance/Obs. jobs  │
└───────────┬──────────────┘
            │ SQL (via ORM)
┌───────────▼──────────────┐
│  SQLite file (local DB)  │   Mimics WMS/WFM/OMS-fed tables.
│  labor_planning.db       │   Seeded from checked-in schema.sql + seed.sql
└───────────────────────────┘
```

This preserves the strict UI/backend separation and API-exposed backend required by [CLAUDE.md](../CLAUDE.md) §2 — the frontend never touches the database directly.

## 3. Stack

| Layer | Choice | Why |
|---|---|---|
| **Local mock data source** | SQLite (single file, `labor_planning.db`) | Zero server setup — anyone cloning the repo gets a working DB from one script, no install beyond Python. Explicitly a stand-in for real WMS/HCM/OMS-fed tables, not a production data store. |
| **Backend** | Python + FastAPI | Fast to build; auto-generates an OpenAPI/Swagger spec, which directly satisfies Feature 10's API-documentation requirement; easy single-command startup for a laptop demo. |
| **ORM / DB access** | SQLAlchemy (sync, SQLite driver) | Keeps a clean layer between API route handlers and raw SQL; makes a later swap to Postgres (production realism) a config change, not a rewrite. |
| **Frontend** | React + Vite (minimal) | Lightweight SPA calling the FastAPI backend over REST/JSON; gives the demo something visual beyond Swagger docs, without committing to a heavy framework. |
| **API contract** | OpenAPI 3.x (auto-generated by FastAPI) | Matches Feature 10's Data Product Catalog & API Layer requirement directly. |

## 4. Repository layout (proposed)

```
/db/
  schema.sql          -- DDL: CREATE TABLE for every ERD entity (Input/Task/Output layers)
  seed_data.sql        -- INSERT statements: representative mock rows for demo/show-and-tell
  init_db.py           -- Convenience script: runs schema.sql + seed_data.sql against a fresh labor_planning.db
/backend/
  app/
    models/            -- SQLAlchemy models, one module per ERD layer (input/task/output)
    api/                -- FastAPI routers, one module per feature (01-master-data, 05-requirements, ...)
    services/           -- Business logic: task generation, headcount calc, matching, governance, observability jobs
    main.py             -- FastAPI app entrypoint
  requirements.txt
/frontend/
  src/
    pages/               -- One page/view per key workflow (e.g., requirements dashboard, plan view)
    api/                 -- Thin HTTP client wrapping backend REST calls
  package.json
/docs/                    -- (existing) planning docs, ERD reference, feature docs
```

This mirrors the Input/Task/Output layering from the ERD reference and keeps each Feature Document's scope mapped to one `services/` and `api/` module, so Feature → code traceability stays clear as sprints land.

## 5. Local data source: schema + seed strategy

- `db/schema.sql` will contain the DDL for every entity across all three ERD layers (Input, Task, Output) — generated to match [labor-planning-erd-reference-v2.md](reference/labor-planning-erd-reference-v2.md) exactly, including the constraints called out there (`std_time_mins > 0`, `required_headcount >= 1`, etc.).
- `db/seed_data.sql` will contain enough representative rows (1 warehouse, a handful of zones/employees/job roles/shift templates/task types, a few orders and forecasts) to make every Phase 1 feature demonstrable end-to-end — e.g., enough to walk through the ERD reference's own worked example (600 units, 0.5 min/unit, 480-minute shift → 1 required picker).
- `db/init_db.py` runs both scripts against a fresh SQLite file, so setup for a new clone is a single command (e.g., `python db/init_db.py`) with no server dependency.
- These files are built alongside Feature 01 (Facility & Org Master Data) in Sprint 1, since that's the first feature needing persisted data — see [RELEASE_PLAN.md](RELEASE_PLAN.md). Each subsequent feature's sprint extends `schema.sql`/`seed_data.sql` for the entities it introduces, rather than one big upfront schema dump — keeping with the "smallest coherent increment" principle in [CLAUDE.md](../CLAUDE.md) §1.
- Explicitly labeled in-repo (README + code comments) as a **mock/demo data source standing in for WMS/WFM/OMS feeds** — never to be mistaken for a production integration.

## 6. Running it locally (for someone replicating the repo)

1. Clone the repo.
2. `python db/init_db.py` — creates and seeds `labor_planning.db` in the repo root (or `/db/`), from the checked-in SQL scripts.
3. `cd backend && pip install -r requirements.txt && uvicorn app.main:app --reload` — starts the API on `localhost:8000`, with Swagger UI at `/docs`.
4. `cd frontend && npm install && npm run dev` — starts the demo UI on `localhost:5173`, calling the backend.

No cloud account, external DB server, or paid service is required to run the full demo end-to-end on a laptop.

## 7. Mapping to the Release Plan

- **Phase 1 (Sprints 1–7)**: `db/schema.sql`/`seed_data.sql` and the corresponding backend models/services/API routes are built incrementally, one feature's slice per sprint, per [RELEASE_PLAN.md](RELEASE_PLAN.md). Minimal frontend views are added per feature as it becomes demoable (e.g., a requirements dashboard once Feature 05 lands).
- **Phase 2 (Sprints 8–9)**: Feature 10 formalizes the OpenAPI contract and conventions already emerging from Phase 1's routers; Feature 08 adds the governance workflow/audit tables to the schema.
- **Phase 3 (Sprint 10)**: Feature 09's health-check jobs run as scheduled backend tasks (e.g., APScheduler) reading the same local SQLite DB — no new infrastructure required.

## 8. Explicit non-goals

- This local SQLite setup is **not** intended to become the production data store — if/when this tool is deployed against a real warehouse, `db/schema.sql` maps to a real DB engine (e.g., Postgres) provisioned separately; the SQLAlchemy layer is chosen specifically to make that swap low-friction later.
- No authentication/authorization is assumed for the laptop-demo scenario in this document — that remains an open question flagged in Feature 10, to be resolved before any real deployment.

## 9. Open Questions

- Exact seed data volume/realism needed for a compelling show-and-tell (single warehouse vs. a couple of warehouses/zones for contrast)?
